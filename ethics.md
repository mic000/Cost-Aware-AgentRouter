## Ethical Considerations

This project uses the AIDev-pop dataset, a public GitHub-based dataset of agentic pull requests. Although the data is publicly accessible, we treat it as human-related software repository data rather than as purely technical records. Following Gold and Krinke's discussion of ethical mining in MSR, repository data may contain information about developers, reviewers, repositories, and organizations through their interactions with code, issues, and pull requests. For this reason, our project considers the ethical risks of using AIDev under the Menlo Report principles: respect for persons, beneficence, justice, and respect for law and public interest.

For respect for persons, the main concern is that GitHub contributors did not directly give informed consent for their PR activity to be reused in our study. In our final processed dataset, we kept most PR-level information needed for the routing task, including PR text, timestamps, agent identity, and merge-related status. We also added a small number of repository-level features, including repository language, forks, and stars, because these features may help describe the task and project context. In addition, we created outcome and merged as result variables for model training and evaluation. At the same time, we removed the PR author's identity, URL links, and most detailed repository information, and we did not use the all_user table at all. This reduces the risk of directly identifying individual developers or building developer profiles.

However, these steps do not fully remove ethical risk. PR text may still contain names, issue references, technical details, or other information that could make a project or contributor recognizable. Repository language, forks, and stars may also make some repositories easier to infer, especially for large or well-known projects. For this reason, we will not report individual usernames, repository names, URLs, or raw examples that could identify a specific developer or project. Our analysis will focus on aggregate patterns across agents, task features, repository-level features, and merge outcomes. If examples are needed in the report, we will paraphrase them or use synthetic examples instead of quoting identifiable PR text.

For beneficence, the expected benefit of the project is to study whether AI coding agents can be selected more efficiently for different software tasks. This may help future research understand the relationship between task features, repository context, agent choice, success probability, and cost. At the same time, the project could create risks if results are interpreted as judgments about individual developers, repositories, or organizations. A low predicted merge probability should not be read as evidence that a developer, maintainer, or project has low quality. Merge status is affected by many factors, including project policy, reviewer availability, task priority, coding standards, and maintainability concerns. We will therefore describe merge outcome as a noisy proxy for PR acceptance rather than a direct measure of code quality or developer competence.

For justice and fairness, AIDev may overrepresent popular repositories, common programming languages, active GitHub communities, or agents that were used more often by early adopters. The agents were chosen by humans in real projects, so the data reflects existing usage patterns rather than randomized assignment. This creates selection bias: an agent may appear more successful because it was used on easier tasks, in more active repositories, or in projects with different review practices. To avoid unfair conclusions, we will report class imbalance, use appropriate evaluation metrics such as Macro-F1, and present results by support size when possible. We will also avoid claiming that one agent is universally better than another. Our claims will be limited to the observed AIDev distribution and the features available in the dataset.

For respect for law and public interest, we will use the dataset only for this course project and follow the dataset's access conditions and relevant platform terms. We will store the data locally for analysis, avoid redistributing raw PR text or identifiable metadata, and only release aggregate tables, model results, and non-identifying feature-importance findings. We will also document our preprocessing decisions, including which fields were retained, which fields were removed, and why the all_user table was excluded. This makes the project more transparent and helps future readers understand the privacy and validity limits of our results.

Overall, our use of AIDev is ethically acceptable only with careful limits. The project is an offline empirical study, not a deployed system for assigning real developers or real issues to agents. We frame the router as a feasibility study for cost-aware agent selection, not as a decision tool ready for use in live open-source communities. This distinction matters because a deployed router could influence which agents are used, which tasks receive attention, and how maintainers evaluate AI-generated contributions. Our report will therefore separate empirical findings from practical deployment recommendations and state the privacy, consent, bias, and proxy-measure limitations clearly.
